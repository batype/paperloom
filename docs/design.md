# 定位与首版取舍

目标用户：写技术说明、经验文章和项目方案的开发者。核心任务是把已有 Markdown 内容整理成能够交付给别人的文档。

2026-10-30 查看官方功能页：[Dillinger](https://dillinger.io/features) 已支持双栏实时预览、MD/HTML/PDF 导出、主题和云同步；[StackEdit](https://stackedit.io/) 提供同步、协作以及扩展语法。Paperloom 不把这些基础能力宣称为独创，选择围绕排版、交付检查和真实 PDF 校样组成更短的交付路径。

首版验证的假设：用户在写完内容后，需要快速得到结构清楚、可离线阅读的交付件。三套版式、内部结构检查和实际 PDF 校样是否减少反复调整，需要真实使用反馈，不能由竞争工具的存在或 GitHub 星标推断。

## 导出设计

PDF 使用 pdfmake 的语义文档模型，保留文字、链接、表格、列表等结构。中文使用本地完整字体，生成时子集嵌入。浏览器截图 PDF 会丢失搜索和选中文字能力，因此不作为默认方案。PDF 排版与 HTML/CSS 不是同一引擎，所以提供实际 PDF 校样，不声称阅读预览与 PDF 逐像素一致。

版式变化不改 Markdown；原始 MD 不带产品专有配置，便于 Git 和其他编辑器继续使用。HTML 是携带 CSS 的独立文件，正文不能注入 HTML/script。PDF 不发送到服务端。

外部图片可能泄露访问行为或在导出时因跨域/鉴权失效，因此首版不自动获取。嵌入本地 PNG/JPEG 能稳定带走。用户可以继续保留原始远程图片语法，工具会明确给出提示，MD 导出不修改其链接。

## 保存与性能

默认保存一份本地草稿，用户可关闭并删除保存副本。替换操作保留一份内存撤销快照。用户主动刷新前最后约 700ms 的编辑可能尚未持久化；重要内容应下载。多标签页同时编辑同一来源时草稿采用最后保存值，当前不做协作合并。

Worker 加上输入/输出约束减少大文档阻塞界面的机会，不承诺任意复杂文档都能排版。PDF 首次加载字体是明确的等待成本；使用同源静态文件、懒加载和状态提示，后续可考虑更细的字体子集服务，但不能以缺字换取表面上的快速下载。

后续候选：多文件工程、本地资源打包、带排版配置的可移植工程、公式与图表语义导出、更多字体、导出样式扩展。在核心路径稳定前不引入账号、付费 AI 和云端数据存储。
